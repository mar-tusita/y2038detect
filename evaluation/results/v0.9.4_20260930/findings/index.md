## 判定基準

各検出は、次の判定のうち1つを付けてレビューします。判定は次の3段階の問いで決まります。

1. **そのコード自体に Y2038 リスクがあるかどうか、判断できるか？**
   判断材料が足りない場合は `unclear`（例: 用途が分からない・外部仕様を確認できない）
2. 判断できる場合、**実際にリスクはあるか？**
   無い場合は `false-positive`（例: 代入元の値が既に演算で範囲限定されている、代入先が
   実質 32-bit で困らない用途しかない、等）
3. リスクがある場合、**そのコード側で対処できるか？**（型を広げる、代替 API に変える、等）
   - 対処できる → `true-positive`
   - 対処できない（原因がファイルシステムのオンディスク形式・通信プロトコル等、
     コード外の固定仕様にある） → `wontfix`

`true-positive`/`false-positive`/`unclear` は「コードが実際に正しいか」という
**correctness の軸**の判定です。`wontfix` はそれとは別の**actionability の軸**
（直せるかどうか）で、`unclear`（判断材料が無く保留）とは区別します。

コーパスでの実例:

- **wontfix**: JFFS2・exFAT の `struct stat` タイムスタンプフィールドアクセス、
  SquashFS の圧縮フォーマット由来のタイムスタンプ。いずれも on-disk 形式が
  32-bit 幅で固定されており、y2038detect が検出したコード側を直しても解決しない
- **false-positive**: `time_t` の値が剰余演算・除算で既に小さい範囲に縮退している、
  `srand()` のようにシード（不透明な値）としてしか使われない、等
- **true-positive**: `time_t` の値をそのまま `int` 等の narrow な型に代入していて、
  代入先の型を広げる余地がある場合
